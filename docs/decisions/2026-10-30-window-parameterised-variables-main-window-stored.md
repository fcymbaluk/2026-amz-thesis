# 2026-10-30 — Window-parameterised variables: the main window is stored, the alternatives are built in the analysis scripts

**Context.** The governing rule for derived variables (`ch4-causal-analysis/GUIDANCE.md`, Methodological standards) stores a derived variable only if it is sample-independent and meets one of three conditions: it needs upstream inputs, it must be computed on the full balanced panel, or it encodes a design decision that has to be identical across all analysis scripts; it sends to the analysis scripts anything sample-dependent or any parameter varied in robustness checks, baseline windows named as the example. The storage audit of phase 2R (task 2.2) met three variables where the two halves of the rule pull apart: the PPCDAm treatment flags (`ppcdam_main` on 2004-2010, `ppcdam_robust` on 2004-2012, `ppcdam_ever_full` over the panel; D-2026-10-12-b) and the normalised outcome on two reference windows (2000-2007 main, 2000-2003 short; D-2026-10-12-f). Each is sample-independent, each is a design decision that every script of a design must share, and each has a window that is a robustness parameter. The pooled price z-scores and the cross-sectional pressure scores raised no such tension: they are sample-dependent and leave the panel (D-2026-10-30-b, -c).

**Decision.** A window-parameterised derived variable is stored in the panel under its main window when that window is itself a logged design decision; every alternative window is built in the analysis scripts, through one shared helper in `_scripts/utils/derived_variables.R`, so that construction is identical and only the window differs. Applied: `enf_ppcdam_listed_main_dum` (D-2026-10-05-h, D-2026-10-12-b) and `env_defor_area_z_bl0007` (D-2026-10-05-h) stay in the final panel; the robust and ever flags stay in the municipality store for script 05's positivity assertions and the audit notebook, and leave the panel (D-2026-10-30-d); the short-window outcome leaves the pipeline (D-2026-10-30-e). The helpers are `listed_within(d, years, name)` and `norm_within(d, x, years, name, sd_floor)`, the functions of scripts 05 and 06 with the column as an argument, plus `z_on(x, ref)` for the standardisations that moved to the analysis scripts. Not pursued: storing all alternatives (the author's first instinct at D-2026-10-12-b), and storing none.

**Rationale.** The third storage condition is a guarantee only if the data carry it: a treated set or an outcome that exists as a column cannot differ between two model scripts, while one that each script rebuilds from a constant can, silently, by a typo in a window. That argues for storing the main definition. The alternatives are the robustness parameters the rule already sends to the analysis scripts, and storing them under fixed names invites a script to use a window other than the one it declares. Storing none would make the main treated set rest on a convention rather than on the data, which is the weaker guarantee for the one definition the chapter's estimates depend on. The cost of the principle is one helper file and a constant with its decision ID at the top of every model script that varies a window, which is what the script template asks of every tunable choice anyway.

**Consequences.** The final panel drops from 85 to 76 columns at phase 2R (with the removals of D-2026-10-30-b and -c and the cattle lag added). Scripts 07 and 11 rebuild the price z-scores on their estimation sample with `z_on()`, and script 07 the two alternative treatment flags with `listed_within()`, at the stage 8 migration (session 2). Candidate designs in `_scripts/models/` declare their treatment window and outcome reference window as named constants citing D-2026-10-12-b and D-2026-10-12-f and call the helpers for any window other than the stored one. The annex states which definitions are stored and which are rebuilt.
